# IP Finder 구현 제안서

보고자료(PDF / PPTX)를 입력받아 특허출원 검토가 필요한 문장을 찾아 하이라이트 마킹하는 온디바이스 도구.
이 문서는 회사 윈도우 PC에서 Claude Opus(Claude Code)에게 구현 브리프로 그대로 전달하는 용도로 작성됨.

## 0. 전제와 보안 원칙

- 실행 환경: 회사 윈도우 PC. **RAM 16GB, GPU 없음.** 모든 문서 처리는 이 PC 안에서만 수행하며 외부 API 호출은 금지.
- 추론은 전부 CPU에서 돌아간다. 설계 전체가 CPU 추론 전제여야 한다 (F절 참조).
- Claude Opus는 **코드를 작성하는 용도**로만 사용한다. 보고서를 판정하는 LLM은 반드시 로컬 모델(Ollama 등)이어야 한다.
- 개발 중 Claude Code 세션에는 실제 비밀 보고서를 절대 넣지 않는다. 테스트용 가짜 PDF/PPTX를 직접 만들어서 쓴다.
  - 실제 보고서는 프로젝트 폴더 바깥의 별도 폴더에 둔다. 프로젝트 폴더에 `.gitignore`와 Claude Code 무시 설정을 두어 `data/real/` 같은 경로가 읽히지 않게 한다.
- 네트워크 차단 검증: 윈도우 방화벽 아웃바운드 규칙으로 `python.exe`, `ollama.exe`를 차단한 상태에서도 전체 파이프라인이 정상 동작해야 한다. 이를 자동 테스트로 둔다.
- 환경변수 고정: `HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`, `PYTHONUTF8=1` (윈도우 한글 로케일 cp949 문제 방지).

## 1. 전체 처리 흐름

```
입력(PDF/PPTX)
  → 파싱: 페이지 → 블록(제목/본문) → 문장, 위치 정보 포함 (공통 중간 표현)
  → 기존 하이라이트 제거
  → 1차 필터: 제목(+본문 앞부분) 기반으로 페이지 선별
  → 2차 판정: 선별된 페이지의 본문을 문장 단위로 판정, 사유/카테고리 산출
  → 마킹: 원본 포맷에 하이라이트 + 사유 메모 기록
  → 출력: 마킹된 파일 + 요약 리포트(md/xlsx)
```

핵심: PDF와 PPTX를 공통 중간 표현으로 변환해 판정 로직은 한 벌만 두고, reader/writer만 포맷별로 분리한다.

## 2. 단계별 방식

### A. 입력 파싱
| 대상 | 방식 | 비고 |
|---|---|---|
| PDF | PyMuPDF | 글자 좌표, 폰트 크기, 주석 접근. 제목은 상단 위치 + 최대 폰트 크기 휴리스틱 |
| PPTX | python-pptx | 제목 플레이스홀더가 명시적이라 제목 추출 정확 |
| 구형 .ppt | PowerPoint COM 자동화(pywin32)로 .pptx 변환 | 회사 PC에 MS Office가 있으면 가장 안정적. 없으면 LibreOffice headless |
| 스캔본/이미지 슬라이드 | 로컬 OCR | 윈도우 내장 OCR(Windows.Media.Ocr, 한국어 언어팩) 또는 RapidOCR/PaddleOCR. 2단계 |

통합 방식 선택지:
- (가) 포맷별 네이티브 처리: PPTX→PPTX, PDF→PDF. 편집 가능성 유지. 구현량 2배. **권장**
- (나) PPTX→PDF 변환 후 PDF만 처리: 구현 단순, 결과물은 PDF 고정. Office COM으로 변환 가능.

### B. 기존 하이라이트 제거
| 유형 | 방식 | 난이도 |
|---|---|---|
| PDF 주석형 Highlight | `/Highlight` 주석 삭제 | 쉬움 |
| PDF 사각형형(PPT 변환본 대부분) | 텍스트 뒤 색 채워진 사각형을 색상·겹침 기준으로 탐지 후 콘텐츠 스트림에서 제거 | 휴리스틱, 오탐 가능 |
| PPTX run 하이라이트 | `a:rPr/a:highlight` 제거 | 쉬움 |
| PPTX 겹친 도형 | 텍스트 박스와 겹치는 반투명 채움 도형 탐지 후 제거 | 중간 |

대안: 제거하지 않고 구분되는 스타일(빨간 테두리 박스, 사이드 코멘트)로만 마킹. 원본 비훼손.
→ 제거를 기본값으로 두고 `--keep-existing` 옵션으로 대안 지원.

### C. 1차 필터: 제목 기반
| 방식 | 장점 | 단점 |
|---|---|---|
| 키워드/규칙 | 즉시, 설명 가능 | 재현율 낮음 |
| 로컬 임베딩 유사도 | 빠름, 의미 기반 | 임계값 튜닝 |
| 로컬 LLM 분류 | 가장 정확 | 페이지당 수 초 |
| 하이브리드 | 균형 | 약간 복잡 |

권장: 하이브리드.
- 규칙으로 명백한 제외(목차, 일정, 비용, 조직도, 감사, 참고문헌) 선처리.
- 나머지는 LLM이 **제목 + 본문 첫 3~5줄**을 보고 판정. 제목만으로는 "개선 방안", "결과" 같은 페이지를 구분할 수 없음.

### D. 2차 판정: 문장 단위 마킹
- LLM에 페이지 본문을 주고 특허 검토 대상 문장을 **원문 그대로** 추출. 출력은 JSON: `{text, reason, category, confidence}`.
- 추출 문장을 원문과 퍼지 매칭(rapidfuzz)해 좌표/run 위치를 찾는다.
- 판정 루브릭(프롬프트 파일 `prompts/rubric.md`로 분리, 사용자가 수정 가능):
  - 포함: 새로운 구조/방법/알고리즘, 기술적 효과와 수치, 문제→해결수단 쌍, 구체적 구현 세부, 기존 대비 차별점
  - 제외: 일정, 비용, 조직, 공지 기술 설명, 단순 결과 요약, 마케팅 문구
- 색상 구분: 노랑 = 검토 권장, 주황 = 강력 후보. 각 마킹에 사유 메모.
- 그림/도표 중심 슬라이드: 텍스트 비중이 낮은 페이지는 "이미지 비중 높음, 수동 검토" 플래그만 붙인다. 비전 LLM 입력은 CPU 환경에서 비현실적이라 GPU 확보 시 검토.

### E. 출력
- PDF: 비파괴 Highlight 주석 + 팝업 코멘트에 사유. 작성자 태그 `IP-Finder`로 일괄 삭제 가능.
- PPTX: run 분할 후 하이라이트, 슬라이드 노트에 사유 기록.
- 요약 리포트: 페이지, 발췌문, 사유, 카테고리, 신뢰도를 md/xlsx로. 특허팀 검토 회의 자료로 사용.

### F. 온디바이스 실행 스택 (윈도우)
| 역할 | 선택 | 비고 |
|---|---|---|
| LLM 런타임 | Ollama for Windows | NVIDIA CUDA / AMD / CPU 지원. localhost만 바인딩. LM Studio 대안 |
| 임베딩 | Ollama의 bge-m3 | torch 의존성 없이 임베딩 가능. sentence-transformers 대안 |
| OCR | Windows.Media.Ocr 또는 RapidOCR | 완전 로컬 |
| Office 연동 | pywin32 COM | .ppt 변환, 슬라이드 이미지 렌더링, PDF 내보내기 |
| Python | 3.12 가상환경 | 3.13+는 일부 ML 라이브러리 호환 미확인 |

### F-1. CPU 전용 전략 (RAM 16GB, GPU 없음)

메모리 예산: OS + Office + Python을 빼면 LLM에 쓸 수 있는 메모리는 약 9~10GB. 14B 이상은 제외. 8B Q4(약 5GB)까지가 현실적 상한.

원칙: **LLM 호출 횟수를 줄이고, 호출할 때 입력을 짧게 유지한다.**
- 1차 필터는 규칙 + 임베딩(bge-m3)으로 처리하고, LLM은 경계 사례에만 호출한다.
- 2차 판정은 1차를 통과한 페이지에만 LLM을 호출한다. 페이지당 1회, JSON 출력, 컨텍스트 창은 2048~4096 토큰으로 제한한다.
- 결과 캐시: 페이지 텍스트 해시를 키로 판정 결과를 저장해, 재실행이나 중단 후 재개 시 LLM을 다시 부르지 않는다.
- 비전 LLM은 CPU에서 너무 느려 1차 범위에서 제외한다. 그림 중심 슬라이드는 "이미지 비중 높음, 수동 검토" 플래그만 붙인다.
- 한 번에 한 모델만 메모리에 올린다. Ollama의 `keep_alive`로 모델 교체 시점을 제어한다.

모델 후보 (Ollama Q4_K_M 기준, 모두 CPU 실행 가능. 제공 버전은 구현 시 확인):
| 역할 | 모델 | 메모리 | 한국어 | 예상 속도 |
|---|---|---|---|---|
| 빠른 판정 (1차 보조, 2차 기본) | Qwen3 4B 또는 EXAONE 3.5 2.4B | 2.5~3GB | 양호 | 페이지당 20~30초 |
| 정밀 판정 (2차 상향 시) | EXAONE 3.5 7.8B 또는 Qwen3 8B | 약 5GB | 우수/양호 | 페이지당 40~60초 |
| 임베딩 | bge-m3 | 약 1.2GB | 양호 | 문장당 수십 ms |

처리 시간 감각 (50페이지 보고서, 1차 필터로 절반 선별, 일반 사무용 CPU 기준 추정):
- 4B 단일 모델: 약 10~15분
- 2차만 8B: 약 20~30분
→ 대화형이 아닌 **배치 작업**으로 설계한다. 진행률 표시, 중단 후 재개, 결과 캐시가 필수.

시작 권장: 4B 한 모델로 1차·2차를 모두 처리해 품질을 확인하고, 부족하면 2차만 8B로 올린다.

LLM 최소화 대안: 과거에 특허로 이어진 보고서 예시가 있으면 bge-m3 임베딩 + 소형 분류기(로지스틱 회귀 수준)로 문장 점수를 매기고, LLM은 상위 후보의 사유 생성에만 쓴다. CPU에서 수 초 내 완료되고 결과가 재현 가능하다.

회사 PC 체크리스트: 모델 다운로드 가능 여부(프록시/보안정책), 관리자 권한(설치), Office 설치 여부, CPU 코어 수와 AVX2 지원 여부.

## 3. 추천 구성과 단계

구성: Python CLI. 공통 중간 표현 + 포맷별 reader/writer, Ollama 백엔드, 하이브리드 필터, 비파괴 마킹 + 사유, 요약 리포트.

```
ip_finder/
  parsers/   pdf_reader.py, pptx_reader.py        → 공통 Document 모델
  cleaners/  pdf_highlight.py, pptx_highlight.py  → 기존 하이라이트 제거
  filters/   rules.py, llm_title_filter.py        → 1차 필터
  judge/     llm_sentence_judge.py, rubric 프롬프트 → 2차 판정
  writers/   pdf_writer.py, pptx_writer.py        → 마킹 기록
  report/    markdown.py, xlsx.py
  llm/       ollama_client.py (localhost 전용, 외부 호스트 금지)
  cli.py
tests/fixtures/  합성 샘플 PDF/PPTX (실제 자료 금지)
```

단계:
1. PDF 한 바퀴: 파싱 → 주석형 하이라이트 제거 → 제목 필터 → 문장 판정 → 주석 마킹 → 리포트
2. PPTX 네이티브 reader/writer 추가, .ppt는 COM 변환
3. 사각형형 하이라이트 제거, OCR. 비전 LLM은 GPU가 생기면 그때 검토
4. 로컬 웹 UI(Streamlit, localhost)에서 제안 마킹을 사람이 승인/거절 후 확정

## 4. 결정 필요 사항

1. PPT 입력의 결과물: PPTX로 받을지, PDF로 받아도 되는지
2. 기존 하이라이트: 제거 vs 구분 스타일로 덧칠
3. 과거 실제 특허로 이어진 보고서 예시 제공 가능 여부 → 루브릭과 few-shot 품질에 직결
4. 그림 중심 슬라이드를 1차 범위에 넣을지
5. 사람 검토 UI 필요 여부
6. 회사 PC: Office 설치 여부, 모델 다운로드 정책, CPU 종류(코어 수, AVX2)
