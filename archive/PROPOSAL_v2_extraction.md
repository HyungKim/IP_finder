# IP Finder 구현 제안서 v2 — 추출 방향

보고자료(PDF / PPTX)를 읽고 **특허출원 검토가 필요한 부분을 추출**해 특허팀 논의 자료로 정리하는 온디바이스 도구.
v1의 "원본에 하이라이트 마킹" 방향은 폐기했다(archive/PROPOSAL_v1_marking.md). 원본 파일은 읽기만 하고 절대 수정하지 않는다.
이 문서는 회사 윈도우 PC에서 Claude Opus(Claude Code)에게 구현 브리프로 그대로 전달하는 용도.

## 0. 전제와 보안 원칙

- 실행 환경: 회사 윈도우 PC, **RAM 16GB, GPU 없음**. 모든 추론은 CPU에서. 외부 API 호출 금지.
- Claude Opus는 **코드를 작성하는 용도**로만 쓴다. 보고서를 읽고 판정하는 LLM은 반드시 로컬 모델(Ollama).
- 개발 중 Claude Code 세션에는 실제 보고서를 절대 넣지 않는다. 가짜 샘플 PDF/PPTX를 생성 스크립트로 만들어 테스트한다.
  실제 자료는 프로젝트 폴더 바깥에 두고, `.gitignore`와 Claude Code 무시 설정으로 접근을 막는다.
- 윈도우 방화벽으로 `python.exe`, `ollama.exe` 아웃바운드를 차단한 상태에서도 전체 파이프라인이 동작해야 하며, 이를 자동 테스트로 검증한다.
- 환경변수 고정: `HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`, `PYTHONUTF8=1`.
- 캐시와 로그에 원문 텍스트를 남기지 않는다. 해시와 판정 결과만 저장한다.

## 1. 목표와 판정 철학

- 목표: 보고서에서 **특허팀과 이야기해 볼 만한 기술 주제를 빠짐없이 뽑는다.** 재현율 우선.
- 이 단계에서 신규성·진보성은 판단하지 않는다. 프롬프트에 "특허성 판단 금지"를 명시한다.
- 구체적 수단이 없어도 효과, 과제, 변경 의도만 있으면 검토 주제다. 효과 뒤에는 수단이 숨어 있다고 가정한다.
- 최종 판단은 사람이 한다. 도구는 후보를 빠짐없이 모으고, **단서 등급**으로 우선순위를 매겨 훑기 쉽게 만든다.

### 추출 기준 (prompts/rubric.md 로 분리, 사용자가 직접 수정 가능)

포함: 아래 중 하나라도 해당하면 추출한다.
| 단서 등급 | 의미 | 예 |
|---|---|---|
| A 수단 명시 | 구조, 구성, 회로, 재료/조성, 공정 조건, 알고리즘, 제어 로직, 파라미터, 설계 값, 절차가 기재됨 | "필터를 2단 LC 구조로 변경", "임계값을 동적으로 조정하는 로직 추가" |
| B 효과 기재 | 성능/품질/비용/수율/신뢰성/속도의 개선·저감·향상, 수치 비교, "기존 대비" | "리플 30% 저감", "검사 시간 절반으로 단축" |
| C 과제 제기 | 문제점, 불량 원인, 한계, 해결 필요 사항 | "고온에서 접착력 저하 발생" |
| D 변경 시사 | 적용, 변경, 도입, 대체, 검토 중, 예정, 신규, 최초, 자체 개발 | "차기 모델에 신규 방식 적용 예정" |

제외: 일정, 비용/예산, 인력/조직, 시장/매출/영업, 고객 요구 나열, 단순 진행 현황(완료/진행 중), 회의 안내, 보고서 주제와 무관한 일반 배경 설명. **확신이 없으면 포함한다.**

등급별 특허팀 논의 포인트(자동 생성):
- A: 기존 방식과의 차이, 변형 가능한 범위
- B: 그 효과를 얻은 구체적 수단이 무엇인지
- C: 해결 수단이 이미 있는지, 시도 중인지
- D: 변경 내용의 구체적 구성

## 2. 출력물

원본 옆에 `<원본명>_검토후보.xlsx` (작업 목록)와 선택적으로 `<원본명>_검토후보.docx` (회의 자료)를 만든다.

### 검토 주제 카드 (한 주제 = 한 행 또는 한 절)
| 항목 | 내용 |
|---|---|
| 번호 | 문서 순서 |
| 주제명 | 한 줄 요약 |
| 단서 등급 | A/B/C/D (여러 등급이면 가장 높은 것, 나머지는 병기) |
| 근거 발췌 | 원문 문장 그대로 + 페이지/슬라이드 번호 + 슬라이드 제목 |
| 논의 포인트 | 특허팀에 확인할 질문 1~2개 |
| 관련 페이지 | 여러 페이지에 걸친 경우 전부 |
| 신뢰도 | 모델 판정 신뢰도. 정렬용이며 제외 기준으로 쓰지 않음 |
| 출처 신호 | (2단계) 저자 강조 여부, 발표자 노트 출처 여부 |

Excel 시트 구성: "주제별"(병합 후), "페이지별"(병합 전 전체 항목), "제외 페이지"(규칙/1차 필터로 제외된 페이지와 사유), "이미지 페이지"(텍스트 없는 페이지 번호만).
Word 회의 자료(2단계): 주제마다 한 절, 근거 발췌와 해당 페이지 썸네일 포함. PDF는 PyMuPDF로 렌더링, PPTX는 Office COM으로 내보내기.

## 3. 처리 흐름

```
입력(PDF / PPTX / .ppt→COM 변환)
  → 파싱: 페이지 → 제목, 본문, 표, (PPTX) 발표자 노트. 좌표 불필요, 읽기 순서만 유지
  → 분할: 불릿/문장 단위로 쪼개고 번호 부여 [1]..[n]
  → 1차 필터(페이지): 규칙으로 명백한 제외 → LLM이 제목 + 첫 3~5줄로 판정, 애매하면 통과
  → 2차 추출(페이지): LLM이 문장 번호 + 등급 + 주제명 + 논의 포인트를 JSON으로 출력
  → 3차 병합(문서): 여러 페이지에 걸친 같은 주제를 하나로 묶고 주제명 확정
  → 출력: Excel (+ Word)
```

핵심 설계:
- **마킹이 없으므로** 좌표 매핑, 하이라이트 제거, 포맷별 writer가 모두 사라진다. reader만 포맷별로 둔다.
- **LLM은 문장 번호로 답한다.** 원문을 다시 출력하지 않으므로 CPU 출력 토큰이 크게 줄고, 퍼지 매칭도 필요 없다.
- 기존 하이라이트는 제거 대상이 아니라 **신호**가 된다. 저자가 강조한 문장은 "저자 강조" 표시를 붙인다(2단계).
- 발표자 노트에는 슬라이드에 없는 세부가 자주 있으므로 기본 포함하되, 옵션으로 끌 수 있게 한다.
- 추출 결과에 문장 번호가 남으므로, 나중에 마킹 기능이 필요해지면 writer 하나를 얹어 v1 방향으로 확장할 수 있다.

### 3차 병합 방식 선택지
| 방식 | 장점 | 단점 |
|---|---|---|
| LLM 한 번에 병합 (항목 요약 목록 전체 입력) | 구성 단순, 주제명 품질 좋음 | 항목 100개 넘으면 컨텍스트 분할 필요 |
| 임베딩 군집 + LLM 이름 붙이기 | 대량 문서에 유리 | 모델 하나 더, 임계값 튜닝 |
| 병합 없이 페이지별 목록만 | 가장 단순 | 같은 주제가 여러 행으로 흩어짐 |

권장: 1단계는 병합 없이 페이지별 목록, 2단계에서 LLM 병합. 항목이 많으면 보고서의 장/절 단위로 나눠 병합.

## 4. CPU 전용 실행 전략 (RAM 16GB, GPU 없음)

메모리 예산: OS + Office + Python을 빼면 약 9~10GB. 8B Q4(약 5GB)가 상한. 한 번에 한 모델만 올린다.

| 역할 | 모델 (Ollama Q4_K_M) | 메모리 | 예상 속도 |
|---|---|---|---|
| 기본 | Qwen3 4B | 약 3GB | 페이지당 30~50초 (추출은 출력이 길어 분류보다 느림) |
| 경량 대안 | EXAONE 3.5 2.4B | 약 2GB | 페이지당 15~30초, 한국어 특화 |
| 상향 | EXAONE 3.5 7.8B / Qwen3 8B | 약 5GB | 페이지당 60~90초 |

50페이지 보고서, 1차 필터로 약 30% 제외 가정:
| 구성 | 예상 시간 |
|---|---|
| 4B, 병합 없음 | 20~30분 |
| 4B, LLM 병합 포함 | 25~35분 |
| 2.4B | 10~20분 |

→ 배치 작업으로 설계. 진행률 표시, 중단 후 재개, 페이지 해시 캐시 필수. 야간 또는 점심시간 실행 전제.

속도 장치:
- 1차 필터는 입력이 짧아 페이지당 5~10초. 전체 시간의 30% 이상을 절약하므로 유지.
- 컨텍스트 창 4096 토큰. 긴 페이지는 문장 번호를 유지한 채 2~3개로 나눠 호출.
- 추출 프롬프트는 루브릭을 압축해 500토큰 이내로.
- `--fast` 옵션: 규칙 기반 단서어(개선, 저감, 향상, 적용, 변경, 신규, 대비, %, 배 등)로 후보 문장만 뽑고 LLM은 주제명과 논의 포인트 생성에만 사용. 수 분 내 완료, 정밀도는 낮음.

## 5. 추천 구성과 단계

```
ip_finder/
  readers/    pdf_reader.py, pptx_reader.py(노트 포함), ppt_convert.py(COM)  → 공통 Document 모델
  segment/    splitter.py       불릿/문장 분할, 번호 부여 (한국어 문장 분리기 kss 또는 규칙)
  filters/    rules.py, page_filter.py   1차 필터
  extract/    page_extractor.py, prompts/rubric.md   2차 추출
  merge/      topic_merger.py   3차 병합 (2단계)
  report/     xlsx.py, docx.py(2단계), thumbnails.py(2단계)
  llm/        ollama_client.py  localhost 전용, 외부 호스트 금지, JSON 재시도
  cache/      sqlite: 키=페이지 텍스트 해시, 값=판정 JSON. 원문 미저장
  cli.py      ip-finder extract <파일 또는 폴더> [--fast] [--no-notes] [--model ...]
tests/fixtures/  합성 샘플 생성 스크립트 (실제 자료 금지)
scripts/compare_models.py  같은 샘플로 모델별 결과·속도 비교 (demo/run_demo.py 가 출발점)
```

단계:
1. **MVP**: PDF/PPTX 읽기 → 분할 → 규칙 + LLM 1차 필터 → 페이지별 추출 → Excel("페이지별", "제외 페이지", "이미지 페이지" 시트)
2. 주제 병합("주제별" 시트), Word 회의 자료 + 썸네일, 저자 강조/노트 출처 신호, 모델 비교 스크립트
3. 폴더 일괄 처리(보고서 여러 건 → 통합 워크북), 이전에 논의한 주제와의 유사 표시(로컬 이력 DB), GPU 확보 시 그림 페이지 처리

## 6. 결정된 사항 (v1 논의에서 유지)

- 구형 .ppt: Office COM으로 자동 변환
- 이미지만 있는 페이지: 검토 대상에서 제외. 페이지 번호만 "이미지 페이지" 시트에 나열
- 결과물: 원본 옆에 새 파일, 원본 미수정
- 1차 필터 입력: 제목 + 본문 첫 3~5줄. 애매하면 통과
- 기술 분야: 전자/반도체/HW, SW/AI/제어, 기계/소재/공정 모두. 루브릭은 분야 공통으로 작성
- 과거 특허화 사례: 제공 불가. 일반 루브릭으로 시작
- 1차 규칙 제외 목록: 목차, 일정, 비용/예산, 조직도/인력, 감사/결론 문구, 참고문헌, 부록 안내
- 신뢰도: 제외 기준으로 쓰지 않음. Excel에는 전부 기록. (Word 회의 자료에는 중간 이상만 싣는 것을 제안)

v1에서 무효가 된 결정: PPTX 출력 포맷, 하이라이트 제거 범위/기록/탐지 기준, 마킹 유형/색상/단위.

## 7. 남은 결정 사항

1. 출력물: Excel만 / Excel + Word 회의 자료 / Word에 페이지 썸네일 포함 여부
2. 단서 등급 A/B/C/D 체계가 특허팀 논의에 맞는지, 조정할 등급이 있는지
3. 주제 병합을 MVP에 넣을지, 2단계로 미룰지 (권장: 2단계)
4. PPTX 발표자 노트 포함 여부 (권장: 기본 포함, 옵션으로 끔)
5. 저자 강조(기존 하이라이트, 볼드, 색상)를 신호로 쓸지 (권장: 2단계에 포함)
6. 정렬: 문서 순서 / 등급 순 / 두 가지 시트 모두 (권장: 둘 다)
7. 여러 보고서 폴더 일괄 처리를 MVP에 넣을지 (권장: 3단계)
8. 기본 모델: 시연 결과 4B는 빠르지만 등급 정확도가 낮고(9/26), 8B는 2배 느리지만 정확도가 높음(13/22). 야간 배치면 8B, 즉시 확인이면 4B + 2단계 등급 판정. 설정으로 교체 가능 (EXAMPLE.md 4절)
9. 캐시: 해시 + 판정 결과만 저장 (권장)
10. 회사 PC: Office 설치 여부, 모델 다운로드 정책(직접 다운로드 가능 / 반입 필요)

## 8. 시연에서 확인된 구현 지침 (EXAMPLE.md 4절, demo/ 참조)

가짜 12장 보고서를 이 맥의 로컬 qwen3 4B·8B로 실제 추출해 본 결과에서 나온 지침. 회사 PC 구현 시 그대로 반영한다.

1. **포함 판단과 등급 판정을 분리한다.** 두 모델 모두 재현율은 충분하지만 등급을 자주 틀린다. 등급 판정은 항목별 짧은 프롬프트 + 등급별 예시 2~3개 + 판정 순서(수단 → 효과 → 과제 → 계획) + 경계 규칙("원인·메커니즘 설명은 C", "효과 수치는 B", "예정·검토는 D").
2. **제외 목록을 예시로 구체화한다.** 클레임 건수, 불량률 현황, 표준·규정 개정, 담당 지정. "확신이 없으면 포함"보다 제외 목록이 우선.
3. **발표자 노트는 반드시 검토하도록 명시**하거나 별도 호출로 처리한다.
4. **주제 병합은 LLM 단발 호출로 하지 않는다.** 4B는 과병합, 8B는 미병합이었다. bge-m3 임베딩 유사도로 묶고 LLM은 주제명만 짓거나, MVP에서는 병합을 생략한다.
5. **qwen3 thinking 계열은 `think=false` 또는 `-instruct` 변형을 쓴다.** 켜 두면 출력 예산이 짧은 호출이 빈 결과가 되고 시간이 2배 든다. JSON 스키마 강제 출력(`format`)은 안정적이므로 모든 호출에 적용.
6. **시간 재추정(회사 PC, CPU 전용).** 50장 기준 4B 20~30분, 8B 35~60분. 병합을 LLM으로 하면 8B 기준 1~2분 추가.
7. `demo/run_demo.py`는 표준 라이브러리만 쓰는 파이프라인 축소판(규칙 필터 → LLM 필터 → 추출 → 병합)이다. 회사 PC에서 Ollama와 모델만 설치하면 바로 돌려 환경 점검과 모델 비교에 쓸 수 있다.

## 9. 결정 로그 (v2 작성 이후)

- 2026-10-26 **LLM 출력은 문장별 등급 라벨 배열만.** 주제명과 질문을 LLM이 생성하지 않는다. 주제명 자리는 발췌 문장 자체를 쓴다.
  근거: 같은 샘플에서 4B 기준 66초 → 8초, 등급 정확도 9/26 → 21/26 (demo/speed_results.json, demo/speed_test2.py).
- 2026-10-26 **논의 포인트(질문)는 등급별 템플릿.** A: 기존 방식과의 차이, 변형 가능한 범위 / B: 이 효과를 얻은 구체적 수단 / C: 해결 수단이 있는지, 시도 중인지 / D: 변경 내용의 구체적 구성.
- 검토 중: 모델 전략(4B / 8B / 혼합), 1차 필터 방식(LLM 제목 판정 유지 여부), 주제 병합 MVP 제외, 전처리 강도, 제목 기반 보정 규칙, 재현율 안전장치, 골드 세트. 결정되는 대로 본문(3~5절)을 다시 쓴다.
